# Canonical WorkItem Contract

> **No WorkItem → No Work.**
>
> Every substantive unit of engineering work — implementation, bug fix,
> investigation, documentation, testing, review, configuration or architecture —
> must be represented by a validated canonical WorkItem before execution begins.

This directory is the control plane. Individual repositories hold WorkItem
**instances**; they MUST NOT redefine the schema, the lifecycle or the policy.

## Source of truth

| Thing | Status |
| --- | --- |
| WorkItem | canonical unit of work |
| WorkItem lifecycle (`state-machine.yaml`) | canonical lifecycle definition |
| WorkItem event | canonical execution/history record |
| Run / `TaskState` | canonical execution state — `agent-fabric`, ADR-0003 |
| WorkPacket | generated dispatch artifact |
| `TODO.md` | **GENERATED projection — non-authoritative** |
| GitHub Issue | external representation and link |
| Pull Request | implementation artifact |
| Dashboard | projection |
| Reporter output | projection and evidence consumer |
| Completion packet | generated WorkItem evidence |

There must be no competing canonical TODO or task representation.

## Where the definitions live

| Concern | File |
| --- | --- |
| Field shapes | `v1.schema.json` |
| States, edges, terminality, delivery-mode skips | `state-machine.yaml` |
| Gate preconditions, forbidden transitions, immutability | `policy.yaml` |
| Size bands and the decomposition rule | `sizing-policy.yaml` |
| Version pinning and provenance | `contract-version.yaml`, `provenance.schema.json` |
| Migration file format | `migrations/README.md` |

Nothing else defines any of these. Downstream code **loads** these files.

## Lifecycle

16 happy-path states:

```text
DRAFT → SPEC_READY → PLAN_READY → READY → IN_PROGRESS
      → IMPLEMENTED → VALIDATED → COMMITTED → PR_DRAFT
      → IMPLEMENTATION_COMPLETE → TESTING → REVIEWING
      → VERIFYING → REPORTING → PR_READY → DONE
```

4 exceptional states:

| State | Meaning |
| --- | --- |
| `BLOCKED` | cannot progress until a stated dependency resolves |
| `FAILED` | execution failed; needs a recovery or re-plan decision |
| `CANCELLED` | terminal; abandoned |
| `CHANGES_REQUIRED` | a review, test or verification round found something |

`CHANGES_REQUIRED` is a real state so repair rounds survive into the event
stream. `VALIDATED`, `TESTING`, `REVIEWING` and `VERIFYING` enter it, and its
only route back into execution is `IN_PROGRESS`.

`FAILED` is reachable only from states where execution has begun. A task that
fails specification or planning has not failed, it has not started.

`IMPLEMENTED` is not `DONE`. `DONE` requires every `required` verification to
have passed **and** a completion packet to exist.

## Two parameters change which edges are legal

- `verification.review_policy` selects which review evidence must have passed
  before `REVIEWING → VERIFYING`. `not_applicable` is not sufficient.
- `delivery.mode: none` makes `COMMITTED`, `PR_DRAFT`,
  `IMPLEMENTATION_COMPLETE` and `PR_READY` unreachable, and short-circuits
  `VALIDATED → TESTING`. Investigations and documentation do not perform a PR
  ceremony.

## Gates

`policy.yaml` carries the full gate table. Gates that can be decided
mechanically are marked `enforced: true` and name the predicate that checks
them; gates needing reviewer judgement are marked `enforced: false` rather than
being silently dropped or falsely machine-checked.

## Identifiers

```text
WI-20261003-0001
```

Immutable, generated by tooling, and never encoding work type. `identity.type`
is metadata and may change as work is refined.

## Acceptance criteria

A criterion is **measurable** when a verifier other than its author can decide
it from recorded evidence, without asking the author's opinion. It must name an
observable condition: a `command` and its expected result, an `artifact` and its
expected property, or a `named_check`. "Code is clean" and "handles the error
case" are not measurable.

Criteria are immutable from `PLAN_READY` onward, so success cannot be defined
retrospectively once implementation has begun.

## Sizing

Bands are declared in `sizing-policy.yaml` and **derived** from
`estimated_context_tokens`. A WorkItem MUST NOT store a decomposition flag; a
stored boolean drifts from the estimate it was derived from.

| Band | Expected context | Execution |
| --- | --- | --- |
| `SMALL` | < 8k | direct |
| `MEDIUM` | 8k–20k | direct |
| `LARGE` | 20k–40k | coordinator decomposition assessment required |
| `XL` | > 40k | decomposition required before execution |

Bands are half-open `[min, max)`, so a band owns values below its own limit.

## Privacy and scope

`scope` and `privacy` are canonical WorkItem fields, promoted from
`agent-fabric`'s `WorkPacket`. A dispatched packet may narrow scope but must
never widen privacy: `CLIENT_CONFIDENTIAL` on a WorkItem forces
`CLIENT_CONFIDENTIAL` on every packet beneath it.

## Versioning

Contract versions are git tags: `workitem/v1`, `workitem/v1.1`, `workitem/v2`.
Consumers pin a ref; they never consume an unpinned `main`. Cached contracts
retain provenance — repo, requested ref, resolved sha, checksum, fetch time.
See `contract-version.yaml` and `provenance.schema.json`.

## Conformance

```bash
python3 -m venv .venv
.venv/bin/pip install -q "jsonschema>=4.21,<5.0" "PyYAML>=6.0,<7.0" \
  "pytest>=7.0.0" "ruff>=0.1.0" "types-PyYAML>=6.0"
.venv/bin/pytest workitem/conformance -v
```

The suite reads this directory as data and never restates it, so it cannot
become a fourth description of the contract. No module under
`workitem_conformance/` names a state, an edge, a band or a rule.

## Relationship to agent execution

A WorkItem is not a Run. `Task == Run`, `TaskState` is the Run lifecycle, and
`WorkPacket` is that Run's dispatch envelope. A Run never sets WorkItem state.
See `harkers/agent-fabric` ADR-0015.
